# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 예외는 아래 "적용 기준"과 "프로젝트별 규칙 우선" 조항에 적힌 것뿐이다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 프로젝트 규칙이 일부만 다루면, 다루지 않은 부분은 이 파일을 따른다.

## 적용 기준

**TDD 필수**

- 비즈니스 로직 (계산, 상태 전이, 검증, 분기 판단)
- API (라우트 핸들러, 요청 파싱, 응답·에러 매핑)
- 유틸 함수 (변환, 파싱, 포맷팅, 정규화)
- 버그 수정 (**버그를 재현하는 실패 테스트가 먼저**)

**TDD 불필요**

- 타입 정의 (interface, type alias)
- 설정 파일 (빌드, 린트, tsconfig, 환경 설정)
- 순수 UI (로직 없는 마크업·스타일 변경)
- SQL (스키마, 마이그레이션, 쿼리 문자열 자체)

판단이 애매하면 **분기·조건·변환이 하나라도 있는지** 본다. 있으면 TDD 필수다.

## RED-GREEN-REFACTOR

### 1. RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트 이름은 기대 동작을 문장으로 쓴다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 셋업으로 실패하면 테스트를 고치고 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 않는다. 테스트를 다시 작성한다.

### 2. GREEN

- **테스트를 통과시키는 최소한의 코드만 작성한다.**
- **YAGNI:** 지금 테스트가 요구하지 않는 분기, 옵션, 일반화, 확장 포인트를 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 테스트를 실행해 확인한다.
- 기존 테스트가 깨지면 다음 단계로 가지 않고 GREEN 안에서 해결한다.

### 3. REFACTOR

- 대상: **중복 제거, 이름 개선, 헬퍼 추출**, 구조 정리.
- 변경할 때마다 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아간다.
- 테스트 코드도 리팩터링 대상이다. 단, 검증 내용은 바꾸지 않는다.

### 4. 반복

- **다음 동작에 대한 RED로 돌아간다.**
- 구현할 동작 목록이 빌 때까지 사이클을 반복한다.

## 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일, 다른 브랜치, 스태시에 보관하는 것 모두 포함된다.
- 삭제한 코드를 보면서 다시 타이핑하지 않는다. 테스트가 이끄는 대로 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 끝난다. 단순한 코드일수록 경계값 실수가 숨어 있고, 나중에 복잡해질 때 안전망이 된다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 구현 후 작성한 테스트는 구현을 따라 쓰게 되어 실패를 본 적이 없고, 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정에 드는 시간이 더 크다. 시간이 없을수록 되돌아가는 비용을 줄여야 한다. |
| "삭제하면 낭비" | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이고, 두 번째 작성은 첫 번째보다 빠르고 낫다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 진짜 버릴 코드라면 TDD 적용 대상 저장소에 커밋하지 않는다. |
