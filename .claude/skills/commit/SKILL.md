# Commit

변경사항을 읽고, 리뷰어가 한 커밋씩 이해할 수 있는 단위로 나눠 커밋한다.

## 1. 변경사항 파악

다음을 실행해 전체 그림을 잡는다.

```bash
git status --short
git diff            # 스테이징 전 변경
git diff --cached   # 이미 스테이징된 변경
git log --oneline -10   # 기존 메시지 스타일 확인
```

- 저장소가 아니면(`not a git repository`) 멈추고 사용자에게 `git init` 여부를 묻는다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 끝낸다.
- 추적되지 않은 파일(`??`)은 내용을 열어 확인한다. 파일 이름만 보고 판단하지 않는다.
- 사용자가 이미 스테이징해 둔 변경이 있으면, 그 묶음을 사용자의 의도로 존중하고 첫 번째 커밋 후보로 둔다.

### 커밋하면 안 되는 것

다음은 커밋 계획에서 제외하고, 제외했다는 사실과 이유를 사용자에게 알린다.

- 비밀 정보: `.env`, `*.pem`, `*.key`, 자격 증명 JSON, 코드에 하드코딩된 API 키·토큰
- 빌드 산출물과 의존성: `dist/`, `build/`, `node_modules/`, 캐시 디렉터리
- 임시·디버그 파일: 스크래치 파일, `console.log`만 추가한 변경 등

`.gitignore`에 빠져 있어 보이면 추가를 제안만 하고, 마음대로 수정하지 않는다.

## 2. 논리적 단위로 분류

"이 커밋 하나만 되돌려도 말이 되는가?"를 기준으로 묶는다.

- 하나의 기능·버그 수정에 필요한 코드, 테스트, 타입은 같은 커밋에 둔다.
- 서로 무관한 변경(예: 기능 추가 + 의존성 업데이트 + 설정 파일 정리)은 나눈다.
- 한 파일에 성격이 다른 변경이 섞여 있으면 `git add -p`(대화형) 대신 hunk를 나눠 패치로 스테이징한다:
  `git diff <file> > /tmp/x.patch` → 필요한 hunk만 남겨 `git apply --cached`.
  분리가 지나치게 까다로우면 한 커밋으로 묶고 그 이유를 메시지 본문에 적는다.
- 변경이 작고 한 가지 목적이면 굳이 쪼개지 않는다. 커밋 하나가 정답일 때가 많다.

## 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<본문(선택): 무엇을 왜 바꿨는지>
```

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자가 체감하는 새 기능, 화면·동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로 두고 구조만 개선 |
| `chore` | 빌드, 의존성, 설정, 문서, 스킬 등 제품 동작과 무관한 작업 |

- 요약은 50자 안팎, 마침표 없이, "~한다/~함" 대신 명사형 또는 "~추가", "~수정"으로 끝낸다.
  - 좋음: `feat: 레트로 데스크톱 테마로 전체 레이아웃 개편`
  - 나쁨: `feat: 수정함.`, `fix: 여러 가지 업데이트`
- 본문은 요약만으로 이유가 드러나지 않을 때만 쓴다. 변경 파일 나열은 쓰지 않는다(diff에 있다).
- `git log`에서 기존 스타일(스코프 사용 여부 등)이 보이면 그것을 따른다.
- 세션에 커밋 attribution 지시(예: `Co-Authored-By` 줄)가 있으면 메시지 끝에 붙인다.

## 4. 커밋 실행

"커밋해줘" 요청 자체를 승인으로 보고, 계획을 묻지 않고 바로 커밋한다. 분류 순서대로, 커밋마다 해당 파일만 스테이징한다.

```bash
git add <파일들>
git commit -m "<요약>" -m "<본문>"
```

- `git add -A`, `git add .`는 쓰지 않는다. 제외 대상이 딸려 들어간다.
- `--no-verify`로 훅을 건너뛰지 않는다. pre-commit 훅이 실패하면 원인을 보고하고 고칠지 묻는다.
- `--amend`, `reset`, `rebase` 같은 이력 변경은 사용자가 요청할 때만 한다.
- push는 하지 않는다. 필요하면 사용자가 따로 요청한다.

## 5. 결과 보고

커밋이 끝나면 다음을 짧게 보고한다. 결과가 마음에 들지 않으면 사용자가 되돌릴 수 있도록 판단 근거를 남긴다.

```
커밋 2개를 만들었습니다.

a1b2c3d feat: 레트로 데스크톱 테마로 전체 레이아웃 개편
e4f5g6h chore: commit 스킬 추가

제외: .env (API 키 포함)
```

- `git log --oneline -n <커밋 수>` 결과를 그대로 보여준다.
- 제외한 파일과 이유, 남은 미커밋 변경이 있으면 함께 알린다.
- 저장소가 아니거나 훅이 실패해 커밋하지 못했다면 그 사실을 분명히 알린다.
